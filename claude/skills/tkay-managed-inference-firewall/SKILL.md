# Crusoe VPC firewall + cross-cluster reachability

## Rule zero: a firewall rule cannot be region-aware

Crusoe vpc-firewall-rules are **pure CIDR + port + direction matching**. There is
no notion of source region, cluster or project. So "cluster A in region X reaches
it but cluster B in region Y does not" is **never** explained by a rule whose
source CIDR covers both. Prove or disprove policy before theorising about it.

**The exoneration test — run this first, always.** Probe a CMK control-plane
endpoint on `:443` in the destination region. Every cluster's
`<name>-<id>.<region>.cmk.crusoecloudcompute.com` is gated by an autogenerated
`cmk-cp-api-access-cp-*` rule whose source is `0.0.0.0/0`. If that fails from the
same source that "the firewall is blocking", **no rule is involved** — it is
routing. Strengthen it by picking a control plane in a *different project*, and by
probing the reverse direction: a rule on subnet S cannot break traffic leaving S.

Ladder, cheapest first:

1. `1.1.1.1:443` / `8.8.8.8:53` — does this node have internet at all?
2. a peer node's private IP in its **own** subnet — is the local fabric fine?
3. destination-region control plane `:443` — policy-free reachability
4. the same probe in **reverse** (destination region -> source node's control plane)
5. only now, the actual service port

Timeout = silent drop (no route / no policy match). `connection refused` = you
reached it and nothing is listening. They mean completely different things.

**MTU cannot explain a failed handshake.** A SYN is ~60 bytes, so a PMTU black
hole (small MTU on the path plus ICMP `frag needed` filtered) always lets the
handshake through and stalls on the **first full-size segment**. Its signature is
`connect OK, then hang on a large body`, never `connect times out`. So if the TCP
connect itself fails, stop considering MTU. Where it IS worth testing — a
connect that succeeds but a large POST that times out — sweep DF pings
(`ping -M do -s <size>`, or busybox `-M do`) against the destination to find the
real PMTU. models-monitor is the realistic victim: envelopes run to ~1MB and
`MAX_REQUEST_BYTES` allows far more, and its `REQUEST_TIMEOUT` failure log looks
identical to a routing failure.

## Reading a rule properly — the console lies by abbreviation

The console renders resource *names* where the API stores resolved CIDRs. Always
re-read the rule as JSON before reasoning about it:

```
CRUSOE_PROFILE=<profile> crusoe networking vpc-firewall-rules list \
  --project-name <project> --json
```

`default-vpc-network` in the sources column is really the whole VPC supernet, a
`/16`, and `default-subnet-<region>` in destinations is that subnet's `/20`. A
rule that looks scoped in the UI is often far broader.

Fields that matter and are invisible in the narrow console view: `direction`,
`action`, `state`, `vpc_network_id`.

**Egress is default-allow, so it is almost never the culprit.** The VPC carries a
blanket `default-allow-tcp-udp-egress` (supernet -> `0.0.0.0/0`, all ports) plus
an ICMP twin; egress rules are a handful out of hundreds, the rest are ingress.
Confirm with a `direction` histogram over the JSON before spending time on the
outbound side.

## CLI mechanics (the part that wastes the most time)

`~/.crusoe/config` holds **profiles**, each with its own key and default project.
Select with `CRUSOE_PROFILE=<name>`; a profile's key can only see its own org's
projects, so `crusoe projects list` under the wrong profile returns almost
nothing and looks like a permissions problem.

Every subcommand takes `--project-name` / `--project-id`. **A rule you cannot
find is almost always a project mismatch, not a missing rule.**

Finding which project a cluster lives in — brute force, and worth it:

```
for prof in <profiles>; do
  CRUSOE_PROFILE=$prof crusoe projects list 2>/dev/null | awk 'NR>2 {print $1}' |
  while read p; do
    CRUSOE_PROFILE=$prof crusoe kubernetes clusters list --project-name "$p" 2>/dev/null |
      grep -i "<cluster-name>" && echo "  ^ profile=$prof project=$p"
  done
done
```

The inbox and the clusters that feed it usually live in different projects under
different profiles, so a rule on the inbox side is written in the inbox's
project, not the cluster's. Derive the mapping with the search above every
time; clusters get moved.

`crusoe projects list` failing with `tls: failed to verify certificate: x509:
OSStatus -26276` is the **sandbox** blocking `api.cloud.crusoe.ai`, not a cert
problem. Re-run with the sandbox disabled.

## IP topology — what is per node, per cluster, per region

| Thing | Granularity | Notes |
|---|---|---|
| Node public IP | **one per node**, 1:1 | **this is the egress source IP** — verified by `ifconfig.me` on many nodes, always equal to the node's `ExternalIP` |
| Node private IP | one per node | from the region's `/20` |
| Control-plane IP | **one per cluster** | `<name>-<id>.<region>.cmk.crusoecloudcompute.com` |
| LoadBalancer VIP | **one per LB Service** | e.g. the inbox LB Service |
| NAT gateway | **none** | all `default-subnet-*` show `nat gateway public ip: none` |

So `kubectl get nodes --context <ctx> -o wide` EXTERNAL-IP **is** the correct source list for an
allowlist. There is no shared egress IP to discover.

**Public blocks do NOT map to regions.** A single cluster's nodes straddle
blocks, so you cannot infer a region from an address, and you cannot write a
per-region source CIDR. Observed shape: one region sits in one block, a second
region mixes two blocks within one cluster, a third sits mostly in a third
block with a few nodes from the first. Re-derive the current picture from
`kubectl get nodes -o wide --context <ctx>` across the clusters.

Corollary: an allowlist intended to mean "all our clusters" has to carry every
public block the nodes use, and adding a cluster can silently need a block you
did not list.

A block is subdivided **per DC**, which is why one block spans regions: each DC
owns a few third octets of the `/16`. Per-DC chunks are real and already used
in rules — existing rules source a `/23` that is exactly one region's range. So
a tighter per-DC CIDR is writable, but re-derive it from live node addresses
rather than assuming a DC owns a whole `/16`.

## There is no inter-region routing inside the VPC

Subnets in different regions share one `vpc_network_id` and one `/16`
supernet, and are **still not L3-connected**. Verified: intra-subnet peer ping
0% loss; every cross-region private-IP ping 100% loss; cross-region private
nodePort connects all fail.

Consequences:

- All cross-region traffic goes over **public** addresses. Cross-cluster service
  access needs a LoadBalancer VIP, not a private IP.
- A supernet source entry on a rule only ever matches **same-region** traffic.
  It looks like it covers the whole fleet. It does not.
- Only the public source CIDRs matter for a cross-region allowlist.

## models-monitor -> inbox specifics

The monitor is `hostNetwork: true`, so its source is the **node's** address, not
a pod IP. It POSTs to `inboxEndpoint`, default the shared inbox LB.
That LB is the only inbox — nothing regional exists to fail over to.

The ingress rule that has to exist on the inbox side, in its project:
sources = every cluster's public block, destination = the inbox subnet's `/20`,
ports = the LB port **and** every nodePort the Service maps (for an
`80:30080` + `9090:30900` Service that is `80, 30080, 30900`). Ingress is
evaluated **post-DNAT**, which is why the destination is the backend subnet
CIDR and not the LB VIP.

A monitor that cannot reach the inbox logs, once per envelope:
`envelope send failed` with `context deadline exceeded (Client.Timeout exceeded
while awaiting headers)` at `sender.go`, and the cluster contributes zero
coverage while looking Running and healthy. `REQUEST_TIMEOUT` is short, so
this is indistinguishable in the log from a slow inbox — probe the port to tell
them apart.

## Probing from inside a cluster — image tooling

No universal tool. Detect before probing, or a broken probe reads as a broken
network (this cost a full round: `sh -c 'exec 3<>/dev/tcp/...'` fails on every
target because `/dev/tcp` is a **bash** feature and the image's `sh` is not bash).

| Image | Has | Probe |
|---|---|---|
| models-monitor | busybox only, and **not on `PATH`** | `/bin/busybox nc -w 6 -z <h> <p>`, `/bin/busybox ping`, `/bin/busybox wget -q -O - http://ifconfig.me/ip` |
| cilium-agent | `/usr/bin/bash`, `/usr/bin/timeout`; no curl/nc/wget | `timeout 6 /usr/bin/bash -c 'exec 3<>/dev/tcp/<h>/<p>'` |

`cilium-*` pods are the best generic probe: present on every CMK cluster,
`hostNetwork: true`, so they measure the node's real path. Use
`-c cilium-agent`.

ICMP to a LoadBalancer VIP or another subnet is usually policy-blocked
regardless of routing (`default-allow-subnet-icmp-*` is same-subnet only), so a
failed ping proves nothing. Use TCP.

## Backbone routing or a firewall rule

A firewall rule is the obvious suspect; rule it out before changing one. Probe a
matrix across regions to endpoints that are open to `0.0.0.0/0`, such as control
planes on `:443`, in both directions, with `1.1.1.1:443` as the control. Failures that are bidirectional, that hit `0.0.0.0/0` endpoints, and
that also hit another project's control plane are Crusoe backbone routing:
escalate to #tech-support, and change nothing in the VPC.

**Separate a source-address theory from a location theory by probing both.**
When every failing node sits in one public block, find nodes that share that
block but live in a different DC and probe from them. Same block with the
opposite outcome rules out any CIDR-matching rule, and the region/DC is the
discriminator.

## Traps

- **Trusting the console's source/destination column.** Re-read as JSON.
- **Assuming a rule is missing** when the CLI is pointed at another project.
- **Reading a region off an IP block.** They are mixed.
- **Believing the VPC supernet covers the fleet.** Same-region only.
- **Deriving an allowlist from anything but node `ExternalIP`s.** They are the
  egress IPs, 1:1, no NAT.
- **Concluding "firewall" from a timeout** without probing a `0.0.0.0/0`
  endpoint and the reverse direction.
- **A probe that fails everywhere, including the known-good control** — the probe
  is broken, not the network. Always include a control target.
- **Pinning an ELB VIP.** They get reassigned. Re-resolve the hostname; never
  hardcode a VIP in a rule or a probe script.
- **Assuming a fixed route restored the service.** The workload may have been
  removed while it was broken. Check it is running before declaring coverage.
